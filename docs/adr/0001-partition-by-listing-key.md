# Partition work by Listing key into 64 fixed hash partitions, not by Category

Ingestion workers are generic, and work is split by the Listing key's hash into 64 fixed partitions rather than by Category (one worker pool per Category, e.g. cars vs apparel). Every Change for a Listing must be applied in source-version order, and a Listing's Primary Category can change between updates. Under Category routing, two updates to the same Listing could land on different workers and race. Partitioning by Listing key sends every Change for a Listing to the same partition, in order, with exactly one writer.

## Considered Options

- **Worker pool per Category.** Rejected for v1: reclassification splits one Listing across pools, and per-Category logic doesn't exist yet. Worth revisiting once a Category needs its own code or much more capacity. At that point it becomes per-Category rules inside the generic worker, not separate routing.
- **`hash % N` workers.** Rejected: changing N moves almost every key.
- **Contiguous ranges of raw keys.** Rejected: keys cluster by Merchant, so one large Merchant ends up on one worker.
- **Python's built-in `hash()`.** Rejected: it's randomized per process, so the same key would land in different partitions.

## Consequences

- `partition = int.from_bytes(sha256(f"{merchant_id}/{merchant_product_id}")[:8], "big") % 64`. SHA-256 is used because DuckDB and Spark SQL can reproduce it. `merchant_id` is generated by the server and never contains `/`, so the key encoding is unambiguous.
- Worker `index` of `N` owns partitions where `partition * N // 64 == index` (contiguous blocks, integer math) and holds an `flock` on each one. A second process can't claim a partition that's already owned. A forked child inherits the lock, so workers spawn and never fork while claiming.
- Offsets are stored **per partition**, as the next position to read plus the Landing log's id, so rescaling moves whole partitions: stop the workers, change N, restart. The new owner resumes from the partition's offset, and no keys are rehashed. Offsets saved against another Landing log are refused.
- There can be at most 64 workers. Raising the cap means repartitioning the Landing log.
- Anything else that needs to change a Listing (e.g. reclassification backfill) appends to the Landing log instead of writing to the Listing Store, so the single-writer guarantee holds.
- Ordering is per partition, so a change that fails must never block its partition. It gets rejected or failed after retries and then skipped. Storage failures, by contrast, stop the worker without advancing the offset.
